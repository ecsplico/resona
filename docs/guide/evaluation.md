# Evaluation & Baselines

`resona eval` runs every fixture of the committed evaluation corpus through one execution profile, scores the results and compares them with the promoted baseline for that profile and platform. A release reaches production only after an organization admin promotes a passing evaluation of it.

## The corpus

`eval/corpus/` is synthetic and non-sensitive. Every file is generated by `eval/corpus/make_corpus.py` and licensed CC0-1.0. `eval/corpus/MANIFEST.json` lists, per fixture, the file, its SHA-256, the source, the license, the exact reference text and the checks that apply.

| Fixture | Kind | Checks |
|---|---|---|
| `de-speech` | German speech (macOS `say -v Anna`), umlauts | WER, CER |
| `de-numbers` | German speech with numbers and dates | WER, CER |
| `silence` | 6 s low-level white noise, no speech | silence insertions (expected transcript is empty) |
| `digital-pdf` | German PDF with a text layer | CER |
| `scan-pdf` | the same kind of text, rasterized (no text layer) | CER |
| `table-columns-pdf` | 3×4 table page and a two-column page | CER, required table cells, reading order |

The corpus hash is the SHA-256 of `MANIFEST.json`. The manifest pins the hash of every file, so the corpus hash covers files and references together. The loader refuses a corpus file that does not match its manifest hash.

Regenerate the corpus (macOS with the German voice Anna):

```bash
uv run --no-project --with reportlab --with pillow --with numpy python eval/corpus/make_corpus.py
```

Regeneration changes the corpus hash. Every baseline must then be measured and promoted again.

!!! warning "No private material"
    Do not add private audio, patient documents or transcripts derived from them to `eval/corpus/`. Keep operator corpora outside Git and outside public artifacts.

## Scoring

Scores are numbers only. Reports and hub records never contain transcripts or Markdown.

- **Audio** fixtures are scored on the result's `raw_text`, the engine transcript before postprocessing.
- **Document** fixtures are scored on `markdown`, because table structure and reading order exist only there.
- **Normalization** is versioned and recorded in every report:
    - `text-v1`: lowercase, `’` → `'`, non-word characters → space, whitespace collapsed. Umlauts are kept.
    - `markdown-v1`: HTML comments removed, then `text-v1`.
- **WER/CER** use `jiwer` on the normalized text.
- **Silence insertions** is the number of words emitted on the silence fixture.
- **Missing cells** is the number of required cell values not found in a Markdown pipe table.
- **Order failures** is the number of reading-order anchors that are not found after the previous anchor.

## The gate

| Check | Fails when |
|---|---|
| Absolute | any missing table cell, reading-order failure or silence insertion |
| Regression | any fixture's WER or CER is more than **0.02 absolute** above the baseline |
| Coverage | a fixture or metric is absent from the baseline (`baseline_required:<id>`), or a baseline fixture was not evaluated (`missing_fixture:<id>`) |

If no baseline exists for the profile and platform, or the baseline was measured on another corpus hash, the outcome is `baseline_required`. That is a nonzero exit, not a pass.

Exit codes: `0` passed, `3` gate failed, `4` `baseline_required`, `1` error, `2` policy denied.

## Running an evaluation

### Local

```bash
resona eval --profile cpu-private --output-dir /tmp/resona-eval-cpu
```

Local mode runs each fixture through the explicit `--local` execution path (the same worker execution subprocess, private, organization polish disabled). It compares with the pinned entry in `eval/baselines.json`. Use it to check a machine before you enroll it. Local runs cannot be promoted.

### Against the hub

```bash
export RESONA_API_URL=https://resona.example.org
export RESONA_API_KEY=<org-admin token>
resona eval --profile mac-private --remote --output-dir /tmp/resona-eval-mac
```

`--remote` submits each fixture as a `purpose=evaluation` job. These jobs need an `org_admin` credential and the `release_id` of a release that is staged on the hub (default: the release from `GET /v1/version`; override with `--release-id`). Only workers that report exactly that release claim them. The CLI waits for the jobs, scores the results and records the summary with `POST /v1/evaluations`. Then it compares against `GET /v1/baselines`. The hub baseline is authoritative in remote mode; `eval/baselines.json` is not used.

Every run writes `report.json` to `--output-dir`: corpus hash, normalization ids, release, runtime versions, model revisions per stage, worker and accelerator per fixture, per-fixture metrics and the gate outcome.

## Promoting a baseline

```bash
resona eval promote <evaluation-id> --report /tmp/resona-eval-mac/report.json
```

Promotion calls `POST /v1/evaluations/{id}/promote` with the baseline revision that run saw as `expected_baseline_revision`. If another admin promoted in the meantime, the hub answers 409 `baseline_revision_mismatch`. The hub checks the gate again itself:

- The first baseline (or the first on a new corpus) needs zero silence insertions, missing cells and order failures (422 `absolute_checks_failed`).
- Later baselines must also pass the regression and coverage checks (422 `gate_failed`).

A successful promotion approves the `(execution profile, platform, release)` tuple for production jobs. The CLI then pins the entry in `eval/baselines.json` under `<execution_profile>/<platform>`: corpus hash, release, runtime versions, normalization ids, model revisions and per-fixture metrics. Commit that file.

## Releases

A worker's release is its installed `resona-worker` version, reported in its heartbeat. The hub's own release (`RESONA_RELEASE_ID`, else the `resona-api` version) is approved for every tuple. Any other release must first be staged on the hub:

```bash
resona-admin release stage --manifest release-manifest.json
```

A staged release runs evaluation jobs only. It runs production jobs for a tuple after an evaluation of it has been promoted.
